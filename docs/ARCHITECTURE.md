# kimo architecture: design constraints

## AC-1: software rasterizer stays the reference; the render graph stays decoupled from executors
User direction: keep the software rasterizer bulletproof; keep the node graph decoupled so a WGPU / compute-shader pass for heavy compositing can slot in later without breaking the MCP contract.

1. **Three layers, one-way dependencies.** (A) Project model + MCP tools (what the user or agent edits) -> (B) render graph IR (a pure data DAG built from the project at time t: nodes = source, transform, effect(kind, params), blend, matte, mask, precomp, adjust, output; edges = images carrying explicit colour space, premult state, resolution and bit depth; deterministic node ids and content hashes) -> (C) executors (CPU reference now, GPU later). Tools never call an executor directly. Effects never read project state, only their node params and input images. The node content hash is the cache key (V3-6) and the signature input (RV-6).
2. **EffectDef registry is the per-effect contract**: id, params schema, input/output colour space and premult declaration, reach (point-op | kernel radius | whole-frame | temporal), cost class, determinism class (exact | approx), implementation table {cpu, gpu: optional}. No GPU impl means that node falls back to CPU (mixed graphs get explicit transfer nodes). RV-16 metadata and RV-13 bounds live in the same record, not in parallel tables.
3. **`trait RenderBackend { capabilities(); execute(&Graph, t, region, &mut Frame) }`.** The CPU backend (the current compositor) is the reference; golden hashes stay bit-exact on CPU. A GPU backend must match CPU within a declared per-effect tolerance (max abs error in f32 plus a perceptual metric) checked by a parity harness over the golden scenes; tolerances are stored per effect and never loosened silently. Exports and goldens default to CPU unless the user opts in with backend "gpu" or "auto". Results and manifests always record backend, adapter and version; a bit-exact claim is only made for CPU.
4. **MCP contract stability.** No tool schema, argument, structured result or error code may depend on the backend. Backend choice is a project/server setting (`render_backend`, `KIMO_BACKEND`) and an optional per-call hint, shown by `kimo_info` and in result metadata. Backend differences are quality/approx metadata (RV-16), never different tool behaviour. The registry golden must be identical with the GPU feature on or off except additive info fields.
5. **Build isolation.** GPU code sits behind a cargo feature `gpu`. No wgpu dependency in the default build; the CPU path has zero GPU imports (test: `cargo tree` without the feature has no wgpu). Headless adapters (lavapipe) in CI for parity tests, skipped with a reason otherwise.
6. **Data layout and lifetime rules.** Frame buffers are contiguous f32 RGBA planes with explicit stride; no pointer-chasing in hot paths; no per-pixel closures across the node boundary; effects are kernels over tiles (the tile is also the dirty-rect unit of V3-3); randomness via explicit seeded counters (no thread-local RNG); no hidden global or thread_local state (V3-2); temporal inputs are explicit edges, not cache reads.
7. **Immediate design implications.** RV-13 bounds come from graph node bounds, not a renderer side effect. RV-16 metadata and RV-15 colour declarations attach to the EffectDef / edge descriptors. RV-6 signatures hash node descriptors, not project JSON. RV-9 draft preview is the same graph at lower resolution (resolution is a graph parameter). RV-25 describe_frame reads graph/bounds. Every new effect is registered with reach, colour and determinism metadata even if only CPU exists.
8. **Staged plan** (after the RV list, user-visible only when measured): G0 extract the render graph IR from `render_frame_opts` behind the existing API with golden bit-identity and graph-hash tests; G1 `RenderBackend` trait + CPU backend wrapper; G2 wgpu feature crate with 3 pilot kernels (colour matrix/grade, gaussian blur, blend) + parity harness + timings on lavapipe and real hardware; G3 expand to glow, glass, shatter and 3D by measured payoff. No speed claims without numbers on real hardware.
9. **Review checklist item for every unit:** does this add backend-visible state or bypass the graph? If yes, reject or justify.
