## 1. Luma formula, by name (quoted from code)
Rec.709 (BT.709) luma coefficients on gamma-encoded output values: Y' = 0.2126 R' + 0.7152 G' + 0.0722 B'.
- crates/kimo-core/src/perception/analysis.rs:29-31 `pub fn luma(&self, i: usize) -> f64 { 0.2126 * self.rgb[0][i] + 0.7152 * self.rgb[1][i] + 0.0722 * self.rgb[2][i] }` (black_frames calls this);
- the same formula as lint_frame quality, crates/kimo-core/src/ext/frame_quality.rs:13.
R', G', B' are the frame the engine renders for output: render_frame, then the colour pipeline's output transform, then 8-bit codes from to_rgba8 (crates/kimo-core/src/render.rs:545, `(v.clamp(0.0, 1.0) * 255.0 + 0.5) as u8`), divided by 255 (analysis.rs:19-27, Image::from_frame; analysis::render at analysis.rs:127). So Y' is in 0..1 with code 0 = 0 and code 255 = 1. The canvas starts opaque black (render.rs:457), so a frame with nothing on it is code 0 everywhere.

## 2. Full range vs limited range
The tool measures FULL-RANGE output codes: 0 is black, 255 is white, and no 16-235 rescaling happens in the tool. Limited-range (video-range) sources are expanded to full range when the engine decodes them: media decode runs ffmpeg with `-vf ...,format=rgba` and `-pix_fmt rgba` (render.rs:156), and ffmpeg's scaler reads the frame's range tag, so a file tagged limited (tv) maps Y=16 to code 0 and Y=235 to code 255. Video black (Y=16) therefore reads as code 0, luma 0: black, not lit. Known limit (stated in the tool description): the tool reads the picture the engine renders and does not guess a range. A limited-range file wrongly tagged full range (pc) is decoded with Y=16 as code 16, luma 16/255 = 0.0627 = 3.1 x L, and is not reported. Fixtures g1 and g2 pin both.

## 3. The rules and the numbers
- Whole-frame rule: a frame is near-black when the MAX luma over EVERY pixel of the frame is at or under luma_max: max_i Y'_i <= luma_max. No pixel share, no mean. min_fraction is dropped from the tool entirely (no such argument). Letterbox bars, a black corner, a dark scene with one brighter object, or a black frame with a logo all have a pixel over the line and are not near-black.
- Fixture line: luma_max L = 0.02 (5.1/255), unchanged from THRESHOLD.md (lint_frame quality's crush_below default). Grey codes 0..5 are at or under L (5/255 = 0.0196), code 6 and up are over (6/255 = 0.0235).
- Tool default luma_max = 0 (only exactly-black frames), untuned, as in THRESHOLD.md. Accepted range 0..1.
- Minimum run length M = 2 frames (tool default min_run 2; every fixture uses 2 unless it says otherwise; accepted 1..6000). Reason: 2 is the smallest length that drops a lone black frame (one dropped or flash frame is not reported, Pally rule b), and it is frozen_frames' default, so the overlap test compares the two tools under the same run rule. Callers who only want real gaps raise it (for example 12 = 0.5 s at 24 fps); min_run 1 shows lone frames.
- Run rule: a run is a maximal stretch of consecutive frames, each near-black. It STARTS at the first frame at or under the line and ENDS at the last one; the run ends at the first frame at or above the line, which is not part of it. Pally's wording is "at or above"; the tool keeps "at or under = near-black" (steer 2's formula, and it is what makes the default 0 mean exactly black), so the two differ only on a frame whose max luma equals luma_max exactly. At L = 0.02 that cannot happen for any 8-bit frame: no 8-bit R',G',B' triplet has Rec.709 luma exactly 0.02 (the nearest, 5,1,46, is 0.0006/255 away, by arithmetic over all codes). A run that reaches the first or last frame of the range starts or ends there and is reported with both ends.
- Brightest pixel: each run carries max_luma = the largest Y' of any pixel in any frame of the run (0..1, 6 decimals) and max_luma_255 = max_luma x 255 (2 decimals). A run of pure-black frames reports exactly 0 and 0.
- Frames are measured at full resolution only (no scale argument: a downscaled copy averages pixels and would lower the max, so a small bright logo could vanish).
- Boundary with frozen_frames: black_frames does not look at motion and frozen_frames gives black no special case. A black run that is also frozen is reported by BOTH tools with the same frame numbers; nothing dedupes them. Stated in the description, asserted by test (j).

## 5. What counts as a miss
Any run start, end, length or max_luma different from the above, or a frame near-black or not against its prediction. A miss is reported with its numbers; no rule or line is moved after this file.
